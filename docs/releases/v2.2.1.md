# v2.2.1 — Workflow Hardening

v2.2.1 strengthens v2.2.0's **user-approved, sequential 2–3-agent workflow**. The user still chooses the agents, goals and individual output handoffs. It does not introduce automatic delegation, tool execution, edits, permissions or an autonomous agent loop.

## Deadline and failure handling

- A workflow receives a **120-second total cancellation budget**, and each agent step receives a **50-second cancellation budget**. The implementation uses linked .NET cancellation tokens, forwards the per-step token to the existing Agent Framework, and returns `status=timed-out` with `failedStep` and `stopReason=timeout` when the timeout is observed.
- **These are cooperative cancellation limits, not a hard kill switch**: an AI provider or underlying I/O that ignores cancellation may prevent prompt termination. User/request cancellation propagates separately and is not mislabeled as a successful workflow.
- After validation, workspace mismatch, timeout or a step failure, no additional step is launched. Completed step results remain in the response; raw exception text is not returned in the workflow error.
- A single workflow runs at a time, and the existing Agent Framework also limits concurrent agent executions. No background workflow persistence or scheduler is added.

## Handoff checks

- Explicit per-receiving-step opt-in remains required. At most 1,600 characters of the previous step's text output can be handed off, never arbitrary agent tool access or newly selected agents.
- Before *any* transfer, a local bounded regex checks the **full previous output**, including text beyond the 1,600-character transfer window, for recognizable private keys, bearer tokens, and credential assignments. If a pattern matches (or scanning times out), the transfer is rejected and the workflow stops before calling the receiving agent.
- Error/report/audit messages do not include the detected string. The transfer guard is not a complete data-loss-prevention system, cannot reliably identify all secrets or prompt injections, and cannot undo content already sent to the selected agent/provider in prior steps. Avoid entering secrets.
- There is no automatic sanitization or automatic approval of model-authored content. The receiving agent sees the previous output only when opt-in is enabled and the bounded guard does not match.
- The unchanged `confirmedWorkflow` semantics continue to require approval of the entire declared step list before the first step runs.

## API

```http
GET  /api/agents/orchestration/status
POST /api/agents/orchestration/execute
```

Status now advertises `maximumWorkflowSeconds=120`, `maximumStepSeconds=50`, `stopsOnTimeout=true`, `sensitiveHandoffScreeningEnabled=true`, and `handoffGuardSelfTestPassed`. Response includes optional `stopReason`; `timed-out` is an additional terminal workflow status.

## Verification

CI checks existing two-agent workflow and unapproved/unknown-agent rejections, hardening status and credential guard self-test (including a credential beyond the 1,600-character truncation point), the absence of tool execution, .NET build/regressions, Android build and JS syntax. Real provider timeout behavior and exhaustive credential detection are not proven by these tests.
