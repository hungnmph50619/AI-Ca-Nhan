# v2.2.3 — Workflow Observability

This milestone adds a **bounded, read-only workflow status snapshot** for troubleshooting user-approved sequential workflows. It does not add autonomous execution, tools, a scheduler or durable workflow storage.

## Observation contract

After each successful `execute` or `resume` API call, the server records **metadata only**: workflow ID, workspace ID, status, requested/completed step counts, failed step, allowlisted stop reason, whether human review is pending, timestamps and elapsed wall-clock milliseconds. No goal text, agent messages, handoff preview, review token, preview digest, model output or exception text is stored in the observation.

The store is server-memory-only and keeps at most **100** recent workflow observations for up to **60 minutes** after each update. Records are lost on restart. Elapsed wall-clock time includes human review waits; it is **not** billable AI time, provider duration or the v2.2.2 active-execution budget. Observation does not resume a workflow or grant permission.

## API

```http
GET /api/agents/orchestration/observability/status
GET /api/agents/orchestration/observability/{workflowId}
```

A workflow observation can be read only from its originating workspace. A nonexistent, expired or cross-workspace ID returns 404; the endpoint does not disclose which case applied. No bulk-list endpoint is exposed.

## Security and limitations

- Metadata may still reveal workflow usage patterns. The API is designed for the existing **single-user local application**; it does not replace authentication/authorization if the app is deployed to the Internet or a multi-user environment.
- Existing workflow responses and pending handoff checkpoints from v2.2.2 **still contain user-selected outputs/previews**, respectively. Metadata-only observability does not eliminate their exposure; do not enter secrets.
- Observations are captured after API responses are created. Invalid requests and cancellations without a completed workflow response are not guaranteed to produce an observation. Observability must not be treated as a complete audit trail.
- The in-memory snapshot is bounded, not a durable metrics backend or cross-process record. Data may be evicted under the capacity limit before the 60-minute retention window.
- Timed-out and declined workflows retain their previous stop-on-error behavior, and explicit user approval remains mandatory before handoff.

## Verification

CI checks observability status, a real user-confirmed workflow observation, absence of a known credential value in the metadata response, cross-workspace 404, existing checkpoint/replay/denial regressions, .NET, Android and JavaScript.
